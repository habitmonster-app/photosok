# 사진쏙

사진·기존 PDF를 정리하고 제출 제한 용량에 맞춘 새 파일을 만드는 한국어 모바일 웹앱. 현재 버전은 v1.7입니다(v1.5 기능 + 설치형 웹앱 + 안드로이드 앱).

## 실행

`dist/` 전체를 HTTP(S) 정적 서버로 제공하세요. 개발용 예: `python -m http.server 8000 --directory dist`. 모듈 Worker와 PDF 도구를 사용하므로 `index.html`을 파일로 직접 여는 방식은 지원하지 않습니다. 파일 공유와 저장 위치 선택은 HTTPS 또는 브라우저가 인정하는 로컬 보안 환경에서 사용할 수 있습니다.

사용자 파일은 이 기기에서 처리하며 서버로 전송하지 않습니다. 앱에 분석 추적·계정·파일 영구 보관 기능은 없습니다. 호스팅 접근 권한은 별도입니다. v1.6부터 설치형 웹앱(PWA)입니다. 첫 방문 때 화면과 주요 도구(pdf-lib, PDF.js, HEIC 변환기)를 기기에 저장해 두고, 이후에는 인터넷 없이도 열고 사진·PDF·HEIC를 처리합니다. PDF.js의 글꼴·CMap 등 부속 자원은 처음 쓸 때 받아 저장합니다.

## 안드로이드 앱 (v1.7)

- `android/`: 웹앱(`dist/`)을 앱 안에 그대로 넣은 안드로이드 앱(Kotlin, WebView). 빌드할 때 `dist/`를 복사하므로 화면·기능 코드는 한 곳(`dist/`)만 고치면 된다.
- 인터넷 권한이 없다. 앱 안 파일은 `https://appassets.androidplatform.net/www/`로 열리지만 실제 통신이 아니라 앱 내부 파일이다.
- 앱이 대신하는 일(`dist/native.js` ↔ `MainActivity.kt`의 `PhotoSokNative`): 사진 저장 → 갤러리 '사진쏙' 앨범, PDF·ZIP 저장 → 다운로드/사진쏙, 다른 앱으로 보내기(공유 창), 갤러리·파일 앱에서 공유받기(최대 20개), 카메라 촬영, 파일 고르기. 앱에서 '모두 저장'은 ZIP 대신 사진을 한 장씩 갤러리에 저장한다.
- 빌드: `main`에 push하면 GitHub Actions(`build-apk.yml`)가 APK를 만들어 Releases에 올린다. 휴대폰에서 Releases의 `photosok.apk`를 받아 설치.
- 서명: 테스트용 고정 키(`android/app/debug.keystore`). 플레이스토어 출시용 키는 따로 만들어 저장소에 넣지 않는다.
- 최소 Android 10. 확인 환경: 브라우저에서 앱 연결부를 모의해 저장·공유 바이트 전달 확인. 실제 기기 설치 확인 전.

## 설치형 앱 (v1.6)

- `manifest.webmanifest`, `sw.js`, `pwa.js`, `icons/`. 홈 화면 추가 시 독립 창으로 실행.
- 공유받기(Android Chrome 설치 시): 갤러리·파일 앱의 공유 메뉴에서 사진쏙을 고르면 최대 20개 파일이 바로 담깁니다. 받은 파일은 기기 캐시에 잠깐 두었다가 앱이 꺼내면 지웁니다. 서버로 보내지 않습니다. iPhone Safari는 웹앱 공유받기를 지원하지 않습니다.
- 업데이트: 앱 파일을 바꾸면 `dist/sw.js`의 `VERSION`을 올리세요. 설치된 앱은 새 버전을 뒤에서 받고 "새 버전이 준비됐어요 · 새로 열기"를 보여줍니다. 처음 설치될 때는 화면을 새로고침하지 않습니다.
- 확인 환경: Chromium(Linux, Pixel 7 에뮬레이션)에서 오프라인 실행, 오프라인 PDF 만들기, 오프라인 HEIC 변환, 공유받기 POST 흐름. 실제 휴대폰 설치·공유는 아직 확인 전입니다.

## 현재 기능

- 사진: 200KB / 500KB / 1MB / 직접 입력(10~40,000KB) 이하 압축. 실제 출력 바이트를 검사합니다. 1KB=1,000 bytes, 1MB=1,000,000 bytes.
- 크기·형식: 긴 변 조절, 정확한 가로·세로(각 100~4,000px), JPG / PNG / WebP 변환. 확대 없이 비율을 유지하며 고정 규격은 흰 여백을 넣습니다. PNG·WebP는 투명도를 유지하고 JPG는 흰 배경으로 변환합니다.
- 일괄 작업: 최대 20장, 원본/결과 비교, 개별 저장·ZIP 저장, 취소와 실패 안내. 설정 변경·실패·취소 때 이전 결과를 남기고 이전 설정임을 표시합니다.
- HEIC/HEIF: 브라우저 기본 디코딩을 먼저 시도하고, 지원하지 않으면 로컬 Worker에서 PNG로 변환합니다. 원본 파일은 수정하지 않습니다.
- PDF: 사진과 기존 PDF를 함께 넣어 최대 20페이지를 선택·정렬·삭제·회전하고 한 PDF로 저장합니다. A4 / 사진 비율 선택, 파일 이름, 저장 전 페이지 미리보기를 제공합니다.
- 서류 보정: 네 모서리를 직접 지정하는 원근 보정, 직사각형 자르기, 결과 미리보기·원본 복원. 자동 테두리 인식은 아닙니다.
- 저장·공유: 지원 브라우저에서는 저장 위치를 선택합니다. 그 외에는 다운로드를 요청하고 파일 열기·다시 다운로드·가능한 경우 공유를 제공하는 안내 창을 유지합니다. 저장 위치 선택 취소는 다운로드를 시작하지 않습니다.

### PDF 저장 방식

| 방식 | 결과 | 제한 |
| --- | --- | --- |
| 용량 맞추기 | 사진과 PDF 페이지를 이미지로 만든 PDF. 전체 1/2/5MB 또는 직접 입력 100~40,000KB 이하 | 기존 PDF의 글자 검색·입력 양식·전자서명은 유지되지 않음. 작은 글씨 보호용 해상도 하한 때문에 목표 용량을 높여야 할 수 있음 |
| 글자 유지 · 합치기 | 기존 PDF 페이지를 복사해 글자·벡터 내용을 유지. 사진도 함께 삽입 가능 | 목표 용량·모든 원본 기능·메타데이터 제거를 보장하지 않음. 기존 PDF 페이지 크기는 유지하고 A4/사진 비율은 새 사진 페이지에 적용 |

기존 PDF 페이지에 서류 보정을 적용하면 해당 페이지는 이미지가 됩니다. 두 방식 모두 OCR, PDF 글자 수정, 전자서명 검증, 제출처 접수 보장은 제공하지 않습니다.

## 처리 한계

- UI 입력은 파일당 40MB, 원본 합계 200MB, 총 20장/페이지입니다. 기존 PDF 한 개도 1~20페이지만 열 수 있습니다. 암호로 보호된 PDF는 거절합니다.
- 사진 Canvas 처리는 최대 24MP / 긴 변 8192px입니다. HEIC 디코딩은 최대 32MP / 긴 변 10000px로 제한하며, 대체 변환 결과는 최대 12MP / 긴 변 4096px입니다. 메타데이터에서 크기를 확인할 수 없는 HEIC, 손상된 파일, 지원되지 않는 코덱은 실패할 수 있습니다. 다중 이미지 HEIC는 대표 이미지 한 장을 처리합니다.
- 서류 보정 결과는 최대 6MP / 긴 변 3000px입니다. 수동으로 지정한 모서리와 이미지 크기를 기준으로 보정하므로 실제 종이의 물리적 비율이나 글자 가독성을 판단하지 않습니다.
- GIF/APNG/애니메이션 WebP는 지원하지 않습니다. JPEG 압축과 축소에는 화질 손실이 있습니다. 고정 규격과 용량을 동시에 충족할 수 없으면 규격을 바꾸지 않고 오류를 알립니다.
- 위치·촬영정보 제외는 기본 켜짐입니다. 다시 인코딩한 사진과 용량 맞춤 PDF는 촬영 메타데이터를 복사하지 않습니다. 옵션을 끄고 원본 그대로 내보내는 경우와 PDF 글자 유지 방식은 예외입니다. 사진 속 글자·얼굴은 제거하지 않습니다.
- 브라우저 다운로드 요청은 실제 파일 저장 완료를 확인한 상태와 다릅니다. 저장 위치 선택 API로 쓰기까지 완료된 경우만 저장 완료로 처리합니다. iPhone/Android 실기기의 파일 앱·외부 앱 공유 동작은 별도 검증이 필요합니다.

## 공개 소프트웨어

PDF 입출력·미리보기에 pdf-lib와 PDF.js, HEIC 대체 디코딩에 heic-to/libheif를 사용합니다. 실행 파일과 필요한 리소스는 `dist/vendor/`에 포함합니다. 버전, 저작권, 전체 라이선스, 소스 및 재빌드 안내는 [`dist/licenses.html`](dist/licenses.html)과 [`dist/vendor/SOURCES.md`](dist/vendor/SOURCES.md)에 있습니다.

아래는 각 버전에서 실제 수행한 검증·측정 기록입니다. 초기 버전의 미지원 항목은 당시 기준이며 현재 기능은 위 설명을 따릅니다.

## v1.0 검증 기록
Chromium 실제 Canvas 기능 검사 11개 통과: 200k/500k/1M byte 이하 출력, 크기/비율, PNG 투명도, JPEG 흰 배경, 작은 원본 유지, 확대 금지, 잘못된 파일, 취소, ZIP 구조. UI에서 비교 슬라이더와 개별/일괄 다운로드 확인, 실제 ZIP CRC 검증. 390px 모바일 및 데스크톱 화면 확인.

- 예시 PNG 7.41MB → JPG 491,212 bytes (500KB 목표)
- 일괄 저장 125,661 bytes 원본 유지 + 191KB JPEG (각 200KB 목표)
- `tests/browser-checks.html` 브라우저 기능 검사 소스

iPhone 실기기 및 Android 다운로드 폴더 저장 UX는 아직 실기기 검증 전입니다.

## v1.1 개선
- 용량과 정확한 가로·세로 동시 지정(100~4,000px): 비율 유지, 확대 없이 가운데 배치, 흰 여백. 용량 충족이 불가능하면 규격을 바꾸지 않고 오류 안내.
- 위치·촬영정보 제외 옵션(기본 켜짐): 작은 원본도 다시 인코딩. EXIF/GPS 제거 검사 통과. 사진 속 시각 정보는 제거하지 않음.
- 설정 변경/재처리 실패/취소 때 이전 결과 유지, 이전 설정 결과 표시.
- 휴대폰 하단 실행/취소/저장 버튼. 지원 환경에서 파일 직접 공유; 비지원 환경에서는 저장 경로. 실제 외부 앱 공유는 검증하지 않았음.
- Chromium 실제 검사 17개 통과. UI에서 600×800 규격 처리, 설정 변경 후 이전 결과 유지, 390px 화면의 하단 처리→저장 전환 확인.
- 사용자 사진/처리 이력은 저장하지 않음. 공개 범위는 기존 소유자 전용 유지.

## v1.2 제출용 PDF
- 첫 화면에서 PDF 한 개 / 사진 파일 중 원하는 결과를 선택. 기존 사진 기능 유지.
- 사진 최대 20장을 PDF 한 개로 묶고, 전체 파일 용량을 1/2/5MB 또는 직접 입력(100~40,000KB) 이하로 조절.
- 실제 PDF 바이트 수로 결과 검증. 페이지 수, 형식, 촬영정보 제외 여부 표시. 제출처 접수·OCR·가독성을 보장하지 않음.
- 페이지 순서 변경, 90도 회전, A4/사진 비율, 파일 이름, 저장 전 페이지 미리보기.
- 작은 글씨 보호를 위해 처리 후 긴 변이 min(원본 긴 변, 1200px) 미만이면 목표 상향 안내. 이 해상도 기준은 실제 가독성 판정이 아님.
- 외부 라이브러리·업로드 없이 브라우저에서 PDF 작성. 기존 PDF 입력·병합·압축, OCR, 텍스트 편집은 미지원.
- 설정 변경 시 이전 PDF 표시, 실패/취소 시 이전 결과 유지. 입력을 모두 지우면 메모리의 결과도 해제.

### v1.2 검증
- `tests/pdf-checks.html`: Chromium 10개 검사 통과. 전체 1MB 제한, PDF 구조와 페이지 순서, A4 여백, 회전, 너무 작은 목표 거절, EXIF/GPS 제거, PDF 입력 거절, 취소, 장수/회전 유효성 확인.
- 검사 PDF: 2페이지 / 454,755 bytes. Poppler `pdfinfo`로 A4·페이지 수·구조 확인하고 두 페이지를 PNG로 렌더링해 배치와 글자 확인.
- 앱 화면에서 생성·저장한 예시 PDF: 2페이지 / 338,370 bytes, 제한 1,000,000 bytes 이하. Poppler 구조 검사 통과.
- UI에서 페이지 미리보기 이동, 이름 변경·저장, 순서 변경 시 이전 결과 표시, 사진 모드 전환·압축 확인.
- 경쟁 앱 대비 완료 시간·재시도 횟수 우위와 모바일 실기기 저장/공유는 아직 비교 검증하지 않음.

## v1.3 처리 성능
- 회전을 최종 Canvas 그리기에 통합: 회전 PDF 페이지당 원본 디코딩 3회→1회, 중간 JPEG 저장 2회 제거. 최종 JPEG 압축 자체는 여전히 손실 압축.
- 실제 인코딩 크기를 이용한 보간 탐색과 중간값 보완으로 1% 품질 단계에서 용량을 맞춤. 큰 출력 후보를 캐시에 누적하지 않음. 확정된 결과는 실제 바이트 제한 이하.
- PDF 조립 시 JPEG Blob을 바로 연결해 이미지 전체를 JavaScript ArrayBuffer로 복사하던 과정 제거. 브라우저 전체 메모리가 0이라는 의미가 아님.
- 같은 설정의 완료 결과 재사용, 사진 추가 시 기존 완료 사진 재계산 생략. 미리보기 창을 닫으면 이미지 참조 해제; 목록 이미지는 지연 로딩.

### v1.3 검증과 측정 한계
- 최종 코드에서 사진 17개, PDF 11개, 성능·회전 비교 45개 검사 통과. 용량 제한, 픽셀 방향, 고정 규격, 투명도, EXIF/GPS 제거 유지.
- Chromium156 / Linux, 결정적 입력 5조건을 개선 전후 각 3회 실행. 원시 결과: `docs/performance-v13.json`.
- 500KB 사진: 인코딩 11→7회, 모두 486,862 bytes·1571×1178px. 200KB 사진: 11→9회, 모두 197,665 bytes·993×745px.
- 회전 PDF 2장: 1MB PNG 입력22→14회, JPEG 입력22→10회, 여유 용량6→2회 인코딩. 디코딩은 모두6→2회. 생성 JPEG의 PDF 조립용 전체 ArrayBuffer 복사는0회.
- 최종 3회 중앙값(ms), 개선 전→후: 사진200KB239.2→252.0, 사진500KB362.8→279.6, PNG PDF1MB1889.1→541.6, JPEG PDF1MB767.6→1353.2, PDF8MB513.0→270.8. 실행 시간은 재측정과 조건에 따라 큰 변동이 있었으며 모든 조건에서 빨라진 것은 아님. 보편적 속도 배수·기기 전체 메모리 절감률을 주장하지 않음.
- UI에서 같은 조건의 PDF/사진 재실행 시 기존 결과 재사용 확인. Android/iPhone 실기기 성능·다운로드·공유 검증은 별도 필요.
- 성능 검사 재현: `tests/performance-checks.html`을 `dist/_qa/`로 복사하고, v1.2 커밋 `be9ae862c98a05b50986bcc8320b17e45af1c277`의 `dist/compress.js`, `dist/pdf.js`를 각각 그 폴더의 `baseline-compress.js`, `baseline-pdf.js`로 제공. 검사 파일은 배포물에 포함하지 않음.

## v1.5 화면·표현 정리

- 사진쏙의 화면을 종이색·잉크색·청록색 조합으로 다시 구성했습니다.
- 브랜드 마크, 파일 안내 그림과 빈 상태 그림은 이 프로젝트에서 직접 작성한 SVG입니다. 원본은 dist/assets/에 있습니다.
- 소개 문구: “보내기 전에, 사진쏙.” 사진은 필요한 크기로, 서류는 한 파일로 준비하는 흐름을 설명합니다.
- 화면 문구와 모드 정보를 dist/ui-copy.js로 모으고, 사진 모드 선택 처리를 별도 함수로 정리했습니다. 압축·PDF·HEIC 엔진과 외부 라이브러리에는 변경이 없습니다.
- 예시 서류는 기능 확인용으로 직접 생성한 가상 자료입니다.
- 이 변경은 디자인·문구·화면 코드 개선이며 상표·특허·라이선스에 대한 법률 검토 완료를 의미하지 않습니다. 외부 라이브러리의 고지와 소스 안내는 유지합니다.
